# 网盘分享链接批量处理工具技术方案

## 一、现有项目能力对比分析

在构建新的批量处理工具前，需明确现有开源项目 YunX 与 TgtoDrive 的能力边界与互补性。以下为两者的核心维度对比：

| 对比维度 | YunX (CYQawa/YunX) | TgtoDrive (walkingddd/TgtoDrive) |
| --- | --- | --- |
| 核心定位 | 安卓端网盘解析与直链下载工具 | 网盘文件管理、元数据刮削与流媒体索引增强工具 |
| 支持网盘 | 夸克、UC、迅雷、百度、123、115、光鸭、蓝奏云等 | 115、123、光鸭 |
| 核心能力 | 单文件解析、直链获取、下载 | 批量转存、影视整理、TMDB 刮削、STRM 生成、Emby 反代 |
| 技术栈 | Kotlin + Jetpack Compose + Room + OkHttp | Python + Docker |
| 开源协议 | AGPL-3.0 | MIT |
| 批量处理 | 不支持（仅逐个操作） | 支持（批量转存与整理） |
| TMDB 支持 | 无 | 支持（影视元数据刮削） |
| STRM 支持 | 无 | 支持（生成播放索引文件） |

## 二、你的目标系统架构

目标系统旨在融合 YunX 的广泛网盘解析能力与 TgtoDrive 的自动化整理能力，整体架构设计为分层解耦模式，包含以下核心模块：

1. 网盘接入层：作为底层基础设施，对接各主流网盘（如夸克、UC、123、115 等）的 API，提供统一的文件列表获取与直链解析接口。
2. 元数据刮削层：负责解析文件名，对接 TMDB API，实现电影/电视剧的季集识别、元数据匹配与中文片名映射。
3. 文件管理层：基于刮削结果，执行批量重命名、目录结构规范化整理以及重复文件去重。
4. STRM 生成层：根据整理后的文件路径与直链信息，生成标准的 `.strm` 播放索引文件，支持增量同步。
5. 流媒体代理层：提供 HTTP 代理服务，拦截播放器的直链请求，处理网盘直链的时效性与 Range 请求转发，保障流畅播放。
6. 任务调度层：统筹批量解析、刮削、整理等耗时任务，提供并发控制、失败重试及进度追踪能力。

## 三、推荐技术选型

为确保系统的高效开发与稳定运行，推荐采用以下技术栈：

- 后端语言：Python。Python 拥有成熟的 TMDB API 生态，且 TgtoDrive 已有大量可复用的成熟实现；其异步 IO 特性非常适合处理批量 HTTP 请求等 IO 密集型任务。
- Web 框架：FastAPI + asyncio。FastAPI 原生支持异步非阻塞，能够轻松应对大量并发的网盘 API 调用与元数据查询。
- 数据库：SQLite / PostgreSQL。开发及轻量级部署推荐使用 SQLite 以降低运维成本；生产环境或高并发场景下可平滑迁移至 PostgreSQL。
- 任务队列：Celery / ARQ。批量网盘解析与刮削属于典型的异步耗时任务，需引入消息队列进行削峰填谷与状态管理。
- 部署方案：Docker。与 TgtDrive 保持一致，便于环境隔离、依赖管理及一键部署集成。

## 四、开发路线图（分阶段）

### 第一阶段：网盘接入层（核心基础）

- 逆向提取 YunX 的 Kotlin 源码，分析并还原各网盘的 API 调用逻辑。
- 使用 Python 编写各网盘的 API 客户端，建议优先攻克 123 云盘、光鸭、夸克及 UC。
- 封装统一的文件列表获取接口与直链获取接口，屏蔽底层网盘差异。
- 重点解决 WebView Cookie 提取、API 签名算法逆向及 Token 自动刷新机制。

### 第二阶段：元数据刮削与文件整理

- 集成 TMDB v3 API（需配置 API Key）。
- 实现“文件名 → TMDB ID”的智能匹配逻辑，推荐使用 `python-tmdb3` 或 `tmdbv3api` 库。
- 编写正则表达式引擎，精准识别电视剧的 Season（季）与 Episode（集）信息。
- 开发可配置模板的文件重命名引擎，并参考 TgtDrive 的影视整理模块优化代码。

### 第三阶段：STRM 生成与流媒体代理

- 实现 STRM 文件生成器，将解析到的最新直链 URL 写入对应文件。
- 开发 STRM 目录同步机制，支持增量更新，避免重复扫描。
- 构建 HTTP 代理服务器，将 Emby/Jellyfin/Plex 等播放器的请求透明转发至网盘直链，并完美支持 Range 请求（拖拽播放）。

### 第四阶段：任务调度与 Web 管理界面

- 搭建批量任务队列，实现并发数控制、异常捕获与失败自动重试。
- 参考 TgtDrive 的 Web UI 设计，开发可视化管理界面。
- 实现配置中心，支持网盘账号、TMDB Key、重命名规则及整理路径的动态管理。
- 编写 Dockerfile 与 `docker-compose` 配置，实现一键容器化部署。

## 五、关键技术难点与解决方案

### 5.1 网盘 API 逆向

YunX 的核心逻辑封装在 Kotlin 代码中，需使用 jadx 等反编译工具进行提取。重点分析请求 URL、Header 签名、Cookie/Token 生命周期。同时需应对网盘的反爬机制，如 IP 封禁、频率限制及设备指纹校验，必要时需引入代理池或模拟设备指纹。

### 5.2 TMDB 元数据匹配

- 电影匹配：提取文件名中的年份与片名，优先精确匹配，失败则尝试模糊搜索。
- 剧集匹配：通过正则表达式匹配 `S01E02`、`第 1 季第 2 集` 等常见命名模式，提取季集号。
- 中文映射：TMDB 以英文数据为主，需建立本地中文片名缓存或调用第三方翻译/别名 API 辅助匹配。
- 缓存机制：将匹配结果持久化至数据库，避免对同一文件重复调用 TMDB API。

### 5.3 直链有效期管理

网盘直链通常具有较短的时效性（几分钟至数小时），直接写入 STRM 极易失效。解决方案为：STRM 中写入本地代理 URL，由代理服务器在收到播放请求时，实时向网盘 API 请求最新直链并进行 302 重定向或流式转发。

### 5.4 批量处理的性能优化

- 并发控制：通过信号量或令牌桶算法限制对单一网盘 API 的并发请求数，防止触发风控。
- 断点续传：在数据库中记录每个文件的处理状态（待解析、已刮削、已生成 STRM），任务中断后可从断点恢复。
- 进度追踪：通过 WebSocket 或轮询接口，向 Web 前端实时推送批量任务的执行进度。

## 六、与 TgtoDrive 的集成策略

针对现有资源，提供两种集成路径：

1. Fork TgtoDrive 并扩展：在 TgtoDrive 现有代码基础上，新增 YunX 支持的网盘（如夸克、UC）。

   优点：开发量极小，直接复用其成熟的 TMDB 刮削、STRM 生成及 Emby 代理逻辑。  
   缺点：需深入理解 TgtoDrive 的整体架构与代码风格，扩展时需注意不破坏原有逻辑。

2. 独立工具 + API 调用：完全独立开发网盘接入层，通过 RESTful API 或消息队列与 TgtoDrive 交互。

   优点：架构解耦清晰，互不影响。  
   缺点：需重复实现刮削与 STRM 逻辑，开发成本高。

推荐策略：采用策略 1（Fork TgtoDrive 扩展）。TgtoDrive 已完美覆盖目标系统中最复杂的元数据刮削与流媒体索引部分，将精力集中于补齐其缺失的网盘解析能力，是性价比最高的路径。

## 七、起步建议

1. 环境准备：Fork TgtoDrive 项目，本地跑通其现有功能，通读核心代码结构（特别是网盘适配器与刮削模块）。
2. 逆向分析：使用 jadx 反编译 YunX 源码，梳理目标网盘（如 123 云盘或光鸭）的登录、列表、直链获取 API 流程。
3. 原型验证：用 Python 实现第一个网盘的 API 客户端，编写测试脚本验证直链获取与有效期。
4. 模块集成：将新网盘客户端以适配器模式接入 TgtoDrive，验证完整的“解析 → 刮削 → 生成 STRM → Emby 播放”链路。
5. 逐步扩展：链路跑通后，再逐步添加夸克、UC 等其他网盘的支持。

> 合规与安全提示：
>
> - 严格遵守各网盘的服务条款，控制 API 调用频率，避免对服务器造成压力。
> - 妥善保管用户的 Cookie、Token 等敏感凭证，切勿明文存储或泄露。
> - 注意开源协议兼容性：YunX 采用 AGPL-3.0 协议，TgtoDrive 采用 MIT 协议。若 Fork TgtoDrive 并引入 YunX 的核心逆向代码，衍生项目可能需要遵循 AGPL-3.0 协议开源，请在开发前做好合规评估。
